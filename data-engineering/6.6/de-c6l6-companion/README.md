# مرفق درس دوكر كومبوز - DE5.6

الملفات دي جاهزة تشتغل على أي Docker Engine عادي. جربها على جهازك.

## الملفات
- `app.py` : سكربت تقرير المبيعات (بايثون ستاندرد ليبراري بس، بيتكلم مع ريدس ببروتوكول RESP مباشرة، مفيش تسطيب مكتبات)
- `sales.csv` : بيانات المبيعات التجريبية
- `Dockerfile` : بناء إيميج التطبيق، أربع أسطر
- `compose.yaml` : ملف كومبوز القياسي: سيرفسين `app` و `db` مع `healthcheck` و `depends_on` بشرط الجاهزية ونيمد فوليوم
- `compose.training.yaml` : ملف خاص ببيئة التسجيل فقط، مش مطلوب عندك (التفاصيل تحت)
- `session.txt` : نص جلسة التنفيذ كاملة من التسجيل بكل الأوامر والنواتج الحقيقية
- `exercises.md` + `exercises-session.txt` : التمارين وحلولها المنفذة فعلًا
- `cheatsheet.md` : ورقة مرجع بمفاهيم وأوامر الدرس

## تجرب من الأول على جهازك
المتطلب الوحيد: Docker Engine متسطب وشغال، مع بلاگن كومبوز (موجود افتراضي في Docker Desktop وفي حزم لينكس الحديثة).

```bash
cd مجلد-الملفات
docker compose up -d --build
docker compose ps
docker compose logs app
docker compose exec db redis-cli GET report:top
docker compose down
```

هتلاقي التطبيق اتصل بريدس، قرا البيانات، وطبع التقرير، وقاعدة البيانات فضلت شغالة في الخلفية لحد `down`.

## فروق بيئة التسجيل عن جهازك (للصدق الكامل)
- ملف `compose.yaml` القياسي اتنفذ في التسجيل مدمج مع `compose.training.yaml`، مش منفصل: تجاوز أمر تشغيل ريدس (`redis-server` مباشرة بدل سكربت التشغيل الأصلي بتاع الإيميج) لأن بيئة التسجيل المعزولة بتعين مستخدم واحد بس وسكربت الإيميج الأصلي محتاج تبديل مستخدم. التشغيل المنفصل للملف القياسي على جهاز عادي متجربش هنا؛ المفروض يشتغل زي ما هو على Docker Engine مدعوم مع Compose v2 ومعمارية متوافقة مع الإيميجات ووصول لدوكر هب، وده متوقع مش متثبت في التسجيل. تجاوز الأمر ده مش حل موصى بيه خارج البيئة دي
- ملكية ملفات إيميج ريدس في التسجيل اتعدلت (المستخدم صفر) عشان البيئة المعزولة، والإيميج المعدل مش مرفق ولا مطلوب
- خدمة الأسماء (الوصول لريدس بالاسم `db`) في بيئة التسجيل اتعملت بحل خاص، لأن الDNS الداخلي بتاع دوكر محتاج صلاحيات شبكة مش متاحة هناك؛ على جهازك دوكر بيعملها لوحده أوتوماتيك
- الإيميجات كانت محملة مسبقًا لأن البيئة من غير إنترنت؛ على جهازك أول `up` هيسحب `redis:7-alpine` و `python:3.12-slim` من Docker Hub أوتوماتيك
- أوامر التسجيل استخدمت `docker compose -f compose.yaml -f compose.training.yaml` لتجميع الملفين؛ على جهازك الأمر القياسي `docker compose ...` لوحده كفاية
- إيميج ريدس الرسمي معلن `/data` كـ VOLUME: من غير named volume دوكر بيعمل anonymous volume بيفضل مع الكونتينر طالما عايش، وبعد مسح الكونتينر وتشغيل واحد جديد (`down` ثم `up` أو `rm` ثم `run`) بيتركب فوليوم مجهول تاني فاضي والقديم بيتساب، وهو قابل للاسترجاع بماونت يدوي لو اسمه معروف بس مش بيرجع تلقائي، فالـ named volume هو اللي بيضمن رجوع نفس البيانات (اتثبت عمليًا على الجهاز)
- سلوك الدرس كله (ترتيب الجاهزية، الشبكة بالاسم، بقاء البيانات بعد `down`، ومسحها بـ `down -v`) اتثبت بالتنفيذ الفعلي في التسجيل، وتعريفات الشبكة والفوليوم والفحص والاعتماد كلها جاية من `compose.yaml` نفسه. بقاء البيانات ده بعد مسح الكونتينرات وإعادة التشغيل، مش ضمانة ضد كل فقدان: ريدس في وضعه الافتراضي بيكتب على الديسك كل ثانية تقريبًا
- النواتج في الجلسات المرفقة حقيقية من تنفيذ فعلي، مش معادة الكتابة ولا متظبطة
